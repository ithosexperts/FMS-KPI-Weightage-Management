WHAT IS ALREADY BUILT, AND WHAT YOU BUILD

Built in the database: the two tables, the two write procedures that enforce every rule in this document, and the guard in sp_Add_FMS_Config. You call them; you do not reproduce their logic in SQL of your own.

You build: the weightage screen, its read queries, the on-screen checks, the two procedure calls, and the change to the doer dropdowns on FMS_Config and on the doer reallocation app.

One write path: the application never runs INSERT, UPDATE or DELETE against Z_KPI_Weightage or Z_KPI_Master. Every change goes through a procedure.

1. What a weightage is

Every doer is measured on one or more KPIs. Today there are two: KPI01, Delay Rate, and KPI02, Task Completion Rate. A doer's day score is the weighted sum of their KPI scores for that day, so the weightages decide how much each KPI counts.

Doer KPI01 score KPI02 score Weightage Day score
Bhupal 80 100 KPI01 0.85, KPI02 0.15 80 × 0.85 + 100 × 0.15 = 83.00
Chandan 80 — KPI01 1.00 only 80 × 1.00 = 80.00

Weightage is set per doer. Most doers carry KPI01 0.85 and KPI02 0.15, but that is a common choice, not a rule. A doer is scored only on the KPIs they are given a weightage for: Chandan above has no KPI02 rows at all.

WHY THIS SCREEN MATTERS: A doer with no weightage is not measured. Their tasks are still completed and timed, but none of it reaches their KPI score. That is why FMS_Config will not accept a doer without a weightage (Section 7).

2. Versions — how a weightage changes

A weightage row is never edited once posted. A change is made by closing the current set and adding a new one. Each set is a version with a start date and, once replaced, an end date.

Field Meaning
EffectiveFromDate The first day the version applies. Chosen on the screen. Today or later — never in the past.
EffectiveToDate The last day it applies. Never entered on the screen. Filled automatically when the version is replaced or the doer is marked inactive: the new start date minus one day. Empty means still in effect.
Active = Y A real version — current, past or waiting to start.
Active = N Voided: replaced before it ever took effect. Ignored by scoring.
WORKED EXAMPLE — BHUPAL (0017)
  • 06-Oct-2026: Set at go-live: KPI01 0.85, KPI02 0.15, from 06-Oct.
  • 11-Nov: HR submits KPI01 0.70, KPI02 0.30 from 12-Nov. The 06-Oct rows get EffectiveToDate 11-Nov and stay Active = Y. Two new rows from 12-Nov.
  • Result: Every day up to 11-Nov is scored at 0.85 / 0.15, including any day recalculated later. From 12-Nov, 0.70 / 0.30. No past score changes.
  • 20-Nov: HR submits KPI01 0.80, KPI02 0.20 from 01-Dec. The 12-Nov rows get EffectiveToDate 30-Nov. New rows from 01-Dec.
  • 22-Nov: HR changes its mind: KPI01 0.75, KPI02 0.25 from 25-Nov. The 01-Dec rows have not started, so they are voided (Active = N). The 12-Nov rows now end 24-Nov. New rows from 25-Nov. The newest submission always wins.

The table enforces: weight between 0 and 1; Active is Y or N; EffectiveToDate not before EffectiveFromDate; one live version per doer, KPI and start date.

3.2 Z_KPI_Master

The KPIs the system can score: KPICode, KPIName, Active. Two rows today. The screen reads it for the KPI dropdown. It has no screen: a KPI exists only when its scoring code is built, so a row is added by the developer as part of that build and never before.

4. The rules

Each rule is enforced twice: by the screen, so the user gets instant feedback, and by the procedure, as the final guard. The screen must never rely on the procedure alone, and the procedure never trusts the screen.

ID Rule
WR1 The doer is selected first.
WR2 The doer list holds employees who are Is Employed = Y, whose TermDate is empty or today or later, and who are not in Management (department 20).
WR3 The doer’s current version, and any version waiting to start, are shown read-only.
WR4 A posted row is never edited or deleted. A change is a new version.
WR5 Each submission is the doer’s complete new set: only the KPIs allocated to them, each once.
WR6 KPIs are chosen from Z_KPI_Master. No typing of codes.
WR7 Each weight is above 0 and at most 1, with at most two decimals. A KPI that does not apply is left out, not entered as 0.
WR8 The weights add up to exactly 1.00.
WR9 Effective From is today or later, not before the doer’s StartDate, and not after their TermDate.
WR10 EffectiveToDate is never entered. It is filled when a version is replaced: new start date minus one day.
WR11 A version waiting to start on or after the new start date is voided. The newest submission wins.
WR12 Closing the old version and inserting the new one happen together, or not at all.
WR13 Two users cannot change the same doer at the same moment.
WR14 Change reason is mandatory. The user is taken from the session, never typed.
WR15 Mark Inactive closes the doer’s version; it is refused while the doer is on any active FMS_Config row.
WR16 Only the role that approves weightages can open the screen. Enforced by the application, not the database.

5. The weightage screen

5.1 Select the doer

A single dropdown, searchable by code and name. Its list:

SELECT DISTINCT EmployeeCode, EmployeeName
FROM dbo.VM_EmployeeMaster
WHERE [Is Employed] = 'Y'
AND (TermDate IS NULL OR TermDate >= CAST(GETDATE() AS DATE))
AND ISNULL(DeptCode, 0) <> 20

DISTINCT is needed: the employee master returns one row per role.

5.2 Show the current weightage — read-only

The version in effect and any version waiting to start, with every column of Section 3.1. Nothing on this grid can be edited.

SELECT * FROM dbo.Z_KPI_Weightage
WHERE DoerCode = @DoerCode AND Active = 'Y'
AND (EffectiveToDate IS NULL OR EffectiveToDate >= CAST(GETDATE() AS DATE))
ORDER BY EffectiveFromDate, KPICode;

If the doer has no rows, show "No weightage set — this doer is not measured".

5.3 Enter the new set
  • An "Add KPI" button adds a row: KPI dropdown + weight. Repeat until the set is complete.
  • The KPI dropdown lists Z_KPI_Master rows with Active = Y, minus any KPI already on the screen.
  • Pre-fill the rows from the current version, so the user changes only what differs. Each row can be removed.
  • Show a running total under the weights, green at exactly 1.00, red otherwise.
  • Effective From: a date picker, defaulting to today. Dates before today, before StartDate or after TermDate are disabled.
  • Change Reason: mandatory text, up to 250 characters.
  • Submit is enabled only when every check in Section 5.4 passes.
5.4 On-screen checks
Check Message to show
At least one KPI Add at least one KPI.
No KPI twice This KPI is already in the set.
Weight above 0, at most 1, two decimals Enter a weight between 0.01 and 1.00.
Total exactly 1.00 Weights must add up to exactly 1.00. Current total: x.xx
Effective From in range Choose a date from today, within the doer’s employment.
Reason entered Enter the reason for this change.
5.5 Submit

One call. The procedure validates again, then voids, closes and inserts in a single transaction.

EXEC dbo.SP_KPI_Weightage_Set
@DoerCode = N'0017',
@EffectiveFromDate = '2026-11-12',
@Weights = N'[{"KPI":"KPI01","W":0.70},{"KPI":"KPI02","W":0.30}]',
@ChangeReason = N'Completion now weighted higher',
@UserCode = N'<logged-in user>';
  • @Weights is a JSON array, one object per KPI: "KPI" is the code, "W" the weight as a number with a dot decimal.
  • On success the procedure returns the new rows. Refresh the grid in 5.2 from the database.
  • On failure nothing has been written. Show the error message as it is — it states the problem (Section 6.3).
5.6 Mark Inactive

For a doer who stays employed but stops being a doer — moved to Management, or to a role with no FMS tasks. Leaving the company is handled by TermDate, not by this button.

  • A "Mark Inactive" button on the selected doer, asking for "Inactive from" (today or later) and a reason.
  • Disable it, with the message "Remove this doer from FMS_Config first", while the doer is on any active FMS_Config row as Doer, Backup Doer or Temp Doer.
EXEC dbo.SP_KPI_Weightage_Inactive
@DoerCode = N'0017', @InactiveFromDate = '2026-12-01',
@ChangeReason = N'Moved to Management', @UserCode = N'<logged-in user>';

It closes the version: EffectiveToDate becomes the day before "Inactive from". It does not set Active = N. To measure the doer again later, submit a new set as usual.

5.7 History

A second tab listing every row for the doer, newest first, voided rows included and marked. Read-only.

SELECT * FROM dbo.Z_KPI_Weightage WHERE DoerCode = @DoerCode
ORDER BY EffectiveFromDate DESC, KPICode;

7. FMS_Config and the doer reallocation app

A task planned for a doer without a weightage is scored in the task queue but never reaches their KPI score. To stop that at the source, only measured doers can be put on a stage.

7.1 Doer dropdowns

The Doer, Backup Doer and Temp Doer dropdowns — on the FMS_Config screen and on the doer reallocation app — list only employees with a weightage in effect today:

SELECT DISTINCT e.EmployeeCode, e.EmployeeName
FROM dbo.VM_EmployeeMaster e
WHERE EXISTS (SELECT 1 FROM dbo.Z_KPI_Weightage wt
WHERE wt.DoerCode = e.EmployeeCode AND wt.Active = 'Y'
AND wt.EffectiveFromDate <= CAST(GETDATE() AS DATE)
AND (wt.EffectiveToDate IS NULL
OR wt.EffectiveToDate >= CAST(GETDATE() AS DATE)));
7.2 The database guard
  • sp_Add_FMS_Config now refuses an active row whose Doer, Backup Doer or Temp Doer has no weightage in effect today (error 53041). Show the message.
  • Any other code that writes Doer_EC, BackupDoer_EC or TempDoer_EC — editing an existing FMS_Config row, or the doer reallocation app — must apply the same rule. Tell us which procedures do this, so the same guard can be added to them.
ORDER OF ONBOARDING A NEW DOER:
  1. HR sets the weightage on the weightage screen, effective today.
  2. Only then is the doer added on FMS_Config.
Taking a doer off: remove them from FMS_Config first, then Mark Inactive.

8. What the user will see in scoring

Event Effect on scores
A new set from date D Days from D use the new weights. Days before D are never recalculated with them.
A KPI left out of the new set From D, the doer gets no rows for that KPI. Earlier days keep theirs.
Mark Inactive from D From D, the doer gets no score rows and drops out of the weekly review.
Version voided before it started No effect: it never applied.

The nightly KPI run (02:00) applies these. A change made today shows in scores from tomorrow morning.
